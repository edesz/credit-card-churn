Phases of Implementation

Machine Learning (ML) was used to identify customers at risk of canceling their credit card services. We used these predictions to

  1. estimate order-of-magnitude business metrics from successfully getting these customers to revert their decision to churn with an assumed 40% success rate
  2. make targeting recommendations by profiling customers based on one of the business metrics
  3. understand the most important predictors that a customer would churn or be retained based on their historical behavioural attribu tes

More details, constraints and high-level assumptions are discussed later during project scoping.

We divided this task into five phases, or sections.

Project Scoping

We started by scoping the project to quantify the magnitude of the business problem facing the client. We did this with two Key Performance Indicators (KPIs) used in the finance industry to measure credit card customer churn.

After determining that the problem facing the client was important and actionable using the provided data, we performed a predictive analysis to address the client’s business problem of identifying customers at risk of churning.

To ensure all team members were working with a single source of truth, the raw customer data .xlsx file was stored in a private Cloudflare R2 bucket. All processed datasets and analysis artifacts were stored in the same bucket. Access keys were generated in order to allow team members programmatic access to the same canonical data.

Analysis

During the analysis phase, we prepared the raw data for use in a ML development workflow. We first split the raw data (../../notebooks/01_split_data.ipynb) into training, validation and test splits. We then performed exploratory data analysis (EDA) on the combined training and validation data split. During EDA (../../notebooks/03_eda_v2.ipynb), we created charts to explore the behavioural and demographic attributes of the bank’s customers in the raw data sample. We concluded this phase by developing a hypothesis about the attributes that would likely be predictors of credit customer churn at the bank.

ML Development

Next, we performed two streams of ML modeling.

Stream 1

In the first stream, we ran cost-sensitive ML experiments (../../notebooks/04_run_validation_experiments.ipynb) using subsets of the existing feature set across the same combination of training and validation data used in EDA. During this process, we identified the best combination of ML model, ML features and feature pre-processing (../../notebooks/03_get_best_validation_experiment.ipynb). We were able to validate the hypothesis developed during EDA about the choice of features that would be predictors of churn.

Next, we used a ML monitoring framework to measure concept drift and data drift during model evaluation on unseen data. i.e. the test data split, which was not seen during model validation. We found these to be negligible (../../notebooks/06_evaluate.ipynb) in the unseen data.

The best model was then trained on all available data and, per the business use-case, used to make inference predictions of all available customers data in the random sample of customer data we were provided. These predictions were used to identify the at-risk customers.

From this cohort, we used an order-of-magnitude estimate of Return on Investiment (ROI)* (../../notebooks/08_estimate_cohort_size_using_roi.ipynb) and (net) savings (../../notebooks/09_estimate_cohort_size_using_savings.ipynb) to determine the optimal cohort of at-risk customers for the client to target, for two scenarios. In scenario 1, we assumed the client’s budget allowed for a total targeting of at most 20,000 dollars. For scenario 2, we assumed that a budget of approximately 80,000 dollars was available to target all identified at-risk customers.

Stream 2

In the second stream, we developed an end-to-end ML pipeline (../../notebooks//13_production_ml_pipeline.ipynb). We demonstrated the performance of this model on the unseen (test split) data. All steps from data retrieval to ML inference were orchestrated in this pipeline. Unlike the first stream, additional features were engineered from the raw customer data. This gave an improvement in the model evaluation scores on unseen data compared to those found in the first stream.

Using the unseen data, at-risk customers were identified and model interpretability was performed. Finally, under the same conditions as scenario 2 from above, the ROI was estimated for the unseen (test split) data.

Data Validation

In order to use the ML workflow developed here with new (unseen) customer data, the new customers should have the same characteristics as those in the sample we used in this project. So, next, during the data validation phase, we developed a data model (../../notebooks/12_validate_data.ipynb) using the Pandera Python library to validate the customer data using two complimentary types of data validation tests.

Example Based Tests

First, we performed example-based data tests. A data schema was defined with with specific rules (e.g. column datatypes, constraints, etc.) and used to validate the data. These tests were focused on whether a specific input (attributes of a single customer) demonstrated the

  1. characteristics
  2. datatype

that we expected based on the sample data we used in ML model development in the analysis phase. These were rigid characteristics, often based on the bounds of data that were observed in the available customer data.

Hypothesis Tests

We also used hypothesis testing against a single column or combinations of columns in the raw customer data. Statistical checks were defined directly in the data validation schema. These were not rigid checks of the data. Instead, their purpose was to verify that the data followed certain statistical distributions or relationships rather than just checking individual values.

Unit Testing

During the analysis phase, we developed several custom Python modules to perform the analysis. So, in the unit testing phase, we used the Pytest Python library to write unit tests for these custom modules. The Coverage Python package was used to measure code coverage in the tests.

Dashboard

Finally, we built a dashboard with recommendations and targeting strategies (../../notebooks/14_create_dashboard.ipynb) generated from the at-risk customers identified in stream 1 using the Python Panel framework.
